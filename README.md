# GameTune

Программа для Windows 10/11 на C# (.NET 8): **анализирует компьютер, находит реальные причины лагов, применяет только подходящие исправления и честно сравнивает «до / после» по замерам.**

Принципы: сначала диагноз, потом лечение. Улучшение подтверждается только замером. Любое изменение можно откатить. Программа прямо говорит, когда проблема в железе. Рискованное включается только по явному выбору. Никаких твиков без подтверждённого эффекта.

## Сборка

Нужен .NET 8 SDK. Собирается и тестируется и в Linux: код, который работает только в Windows, помечен `[SupportedOSPlatform("windows")]` и вызывается после проверки ОС.

```bash
dotnet build
dotnet test
```

Один exe-файл для Windows (самодостаточный, .NET на целевом ПК не нужен):

```bash
dotnet publish src/GameTune.Cli -c Release -p:PublishForWindows=true -o artifacts/win-x64
```

Программа запрашивает права администратора: они нужны для ядерного ETW, HKLM, BCD и powercfg.

## Использование (CLI)

```
gametune analyze  [--out profile.json] [--dpc 30] [--net]
gametune plan     --goal latency|smooth|fps|stream|quiet [--profile profile.json]
gametune apply    --goal <цель> [--fix ID,ID] [--option ID:key=value] [--yes]
gametune rollback --fix ID | --session ID | --all
gametune history
gametune measure  --out before.json [--runs 3] [--duration 60] [--warmup 10] [--process game.exe]
gametune compare  before.json after.json [--csv frames.csv]
gametune latency  [--seconds 60]
gametune net      [--target 1.1.1.1] [--no-load]
```

Типичный сценарий:

1. `gametune analyze` — профиль и отчёт о проблемах сохраняются в `C:\ProgramData\GameTune\reports\`.
2. `gametune measure --out before.json` — 3 прогона по 60 с в игре.
3. `gametune plan --goal fps` — план и точный список изменений (сухой прогон, ничего не записывается).
4. `gametune apply --goal fps` — точка восстановления, журнал, применение. Спорные настройки (HAGS, таймер) применяются по одной через `--fix`.
5. Перезагрузка, если нужна, затем `gametune measure --out after.json`.
6. `gametune compare before.json after.json` — если стало хуже: `gametune rollback --session <id>`.

`plan --profile файл.json` работает на любой ОС: эмулирует применение на сохранённом профиле. Удобно для проверки правил без реального ПК.

Опции исправлений: автозагрузка отключается только для перечисленных пунктов (`--option STARTUP_DISABLE:items=Teams;Spotify`). При включённом BitLocker сброс BCD требует подтверждения (`--option BCD_TIMERS_RESET:bitlockerAcknowledged=1`). Для HAGS вариант задаётся явно (`--option HAGS_AB:variant=on|off`).

### Безопасность изменений

Исправления меняют систему только через `ChangeContext.Set`. Этот метод:

1. читает текущее значение; если прочитать не удалось, изменение не выполняется;
2. **сначала** записывает исходное значение в журнал. Если в журнале уже есть активная запись по этой настройке, берётся её исходное значение, так что оригинал не затирается;
3. только после этого меняет настройку. Если запись не удалась, строка журнала удаляется.

Если исправление падает на середине, уже сделанные им изменения откатываются. Все виды настроек (реестр, BCD, питание, экран, сетевой адаптер, файлы) реализуют один интерфейс `IStateBackend`, поэтому откат — это запись исходного значения через тот же бэкенд. Файлы (сцены OBS) перед изменением копируются в `C:\ProgramData\GameTune\backups\`.

### Честное сравнение

- Метрики: средний FPS, 1 % и 0,1 % low (среднее худших кадров), фреймтайм — медиана, p95, p99, стандартное отклонение.
- Первые N секунд прогрева отбрасываются.
- 95 % доверительный интервал считается **блочным бутстрепом**: блоки примерно по 1 секунде, чтобы учесть, что соседние кадры зависят друг от друга. Seed фиксирован, поэтому результат воспроизводим.
- «Лучше» или «хуже» — только если интервалы не пересекаются **и** разница больше разброса между прогонами. Иначе — «в пределах шума».
- Прогоны с троттлингом исключаются из расчёта и помечаются. Если условия различаются (процесс, разрешение, экран, питание), сравнение помечается как ненадёжное.

## Известные ограничения

- **Код для Windows (коллекторы, бэкенды, ETW, P/Invoke) собран, но не запускался на Windows** — сессия разработки шла в Linux. Перед использованием нужна проверка на реальных машинах (раздел 11 ТЗ), лучше всего сначала в виртуальной машине со снимком.
- Режим вывода (Independent Flip / Composed) пока не определяется: нужен разбор событий DxgKrnl, как в PresentMon.
- Температура CPU берётся из ACPI thermal zone (приблизительно); температура GPU и троттлинг — только для NVIDIA через `nvidia-smi`. LibreHardwareMonitor и ADLX — в планах.
- HKCU-исправления (привязка GPU, Game Mode) пишутся в раздел пользователя, от имени которого запущена программа. Если права администратора получены через другую учётную запись, это будет не тот пользователь.
- Наличие MUX определяется косвенно: известно точно, только если встроенный экран уже работает от dGPU.
- `POWER_THROTTLING_OFF` глобальный: Windows не даёт постоянно отключить его для отдельного процесса. Поэтому он умеренного риска и по умолчанию отмечен только для целей «FPS» и «задержка».
